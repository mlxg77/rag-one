# rag-one v2.5 学习规划

## 1. 版本定位

v1.0 已经完成基础 RAG 链路：

```text
文档加载 → 文本切分 → Embedding → 向量检索 → LLM 回答 → 引用展示
```

v2.0 已经完成召回与排序链路：

```text
向量召回 ─┐
           ├→ RRF 融合 → Reranker → Top-K → LLM
BM25 召回 ─┘
```

v2.5 不继续堆叠新功能，而是一个“收敛、加固与学习验收”版本。它集中解决 v2.0 复盘中暴露的四类问题：

1. 功能完成与质量达标的状态混在一起；
2. 索引切换、双索引一致性和实验复现还不够严谨；
3. 最终语料上的 chunk 实验、保留测试集和引用质量仍有缺口；
4. 项目目录、README 和历史实验记录逐渐混杂，不利于继续学习和维护。

v2.5 的核心学习原则：

> 不增加检索花样，先让现有结论可信；不只证明代码能运行，还要证明实验可复现、失败可恢复、结果能解释、知识能由学习者亲自讲清楚。

## 2. 当前基线

v2.5 从以下已验证状态开始，不重新解释或回填历史结果：

| 项目 | 当前状态 |
|---|---|
| 冻结语料 | 10 份文件，指纹记录在 `data/eval/corpus-version.md` |
| 切分参数 | `CHUNK_SIZE=800`，`CHUNK_OVERLAP=150` |
| 当前 chunk | 原始语料、Chroma、BM25 均为 111 条 |
| 固定问题 | 32 道 |
| 检索模式 | vector / bm25 / hybrid / hybrid_rerank |
| 离线测试 | 65 个用例通过 |
| E4 Recall@5 | 100%（31/31 个有 chunk 标注的问题） |
| E4 MRR@10 | 1.000 |
| E4 答案正确率 | 100%（32/32） |
| E4 引用准确率 | 79.3%（23/29），未达到 90% 目标 |
| E4 拒答准确率 | 100%（3/3） |

这里的 `baseline-v1` 应理解为“v1 纯向量算法在 v2 冻结语料上的对照基线”，不是 v1.0 发布时旧语料上的历史成绩。v2.5 文档必须统一使用这个口径。

## 3. v2.5 目标

### 3.1 必须完成

- [ ] 明确区分“已实现、已测试、已通过质量指标、已完成学习验收”
- [ ] 整理整个项目目录结构，拆分当前说明、版本规划、实验报告和学习笔记
- [ ] 将向量索引与 BM25 索引作为同一版本发布，任一环节失败时旧版本仍可使用
- [ ] 为索引和评估产物补齐语料、参数、模型、代码版本等复现信息
- [ ] 在最终 111-chunk 语料上重新完成 chunk 参数实验
- [ ] 保留现有 32 题作为回归集，新增冻结的独立保留测试集
- [ ] 为多片段问题增加“必要证据是否完整”的评估口径
- [ ] 将 E4 严格引用准确率从 79.3% 提升到约定目标
- [ ] 补齐索引切换、版本不一致、评估框架和异常 API 响应测试
- [ ] 完成一次由学习者主导的口头或书面学习验收
- [ ] 发布 v2.5 复盘报告，清楚写出仍未解决的问题

### 3.2 暂不实现

- Query Rewriting / Multi-Query
- 多轮对话与历史问题改写
- Agent 与工具调用
- LangChain / LangGraph 重构
- 父子块检索、上下文压缩等新检索策略
- OCR、图片、表格和多模态解析
- 知识图谱
- 用户系统、权限和多租户
- 微服务、分布式向量数据库和云部署
- 额外引入一套自动 LLM Judge 系统

这些方向均不属于 v2.5。只要一个改动不能直接改善工程可信度、实验可信度、引用质量或学习效果，就留到后续版本。

### 4.1 目录整理原则

1. 先移动文件、修复 import 和命令，不同时修改业务逻辑；
2. 移动前后必须使用同一批测试证明行为没有变化；
3. `README.md` 不再保存全部开发流水账；
4. 历史实验原文保留，但必须标明当时的语料、题数和参数，不使用“当前”描述历史状态；
5. 数据集、运行结果和文档分别归档，机器可读 JSON 与人工报告保持同名；
6. 路径由配置模块或命令参数提供，不在多个脚本里重复硬编码；
7. 如果采用 `src/rag_one/` 包布局，统一通过 `pip install -e .` 安装开发版本，不依赖当前工作目录碰巧可导入。

### 阶段二：整理项目目录结构

#### 学习目标

#### 验收清单

### 阶段三：实现双索引版本化与安全发布

#### 学习目标

理解“先建后切”为什么仍可能在切换窗口失败，以及如何用不可变版本和原子指针避免半发布状态。

#### 建议方案

每次重建生成一个唯一 `index_version`，例如：

```text
20260927T183501Z-a1b2c3d4
```

同一版本包含：

```text
Chroma collection: rag_docs__20260927T183501Z_a1b2c3d4
BM25 file:         storage/bm25/20260927T183501Z-a1b2c3d4.json
Manifest:          storage/index-manifests/20260927T183501Z-a1b2c3d4.json
Active pointer:    storage/active-index.json
```

构建流程：

```text
加载与切分
  ↓
计算语料指纹和 chunk 清单
  ↓
构建版本化向量索引 + 版本化 BM25 索引
  ↓
校验数量、ID 集合、语料指纹、可查询性
  ↓
写入完整 manifest
  ↓
os.replace() 原子切换 active-index.json
  ↓
新请求读取同一个 active version
```

旧版本在新指针成功发布前绝不删除。旧索引清理由独立命令完成，并至少保留最近一个可回滚版本。

#### Manifest 至少记录

```json
{
  "index_version": "...",
  "corpus_sha256": "...",
  "chunk_size": 800,
  "chunk_overlap": 150,
  "chunk_count": 111,
  "chunk_ids_sha256": "...",
  "embedding_model": "BAAI/bge-m3",
  "vector_collection": "...",
  "bm25_file": "...",
  "built_at": "...",
  "git_commit": "..."
}
```

#### 失败注入验收

- [ ] Embedding 失败时 active version 不变
- [ ] Chroma 写入失败时 active version 不变
- [ ] BM25 写入失败时 active version 不变
- [ ] 数量或 chunk ID 校验失败时 active version 不变
- [ ] manifest 写入失败时 active version 不变
- [ ] active pointer 替换失败时旧版本仍可查询
- [ ] 不可能出现向量索引为新版本、BM25 仍为旧版本的激活状态
- [ ] 可以明确回滚到上一个版本

### 阶段四：补齐实验复现信息

#### 学习目标

理解“有一份 JSON”不等于实验可复现；实验结果必须能够回答使用了什么代码、语料、索引、参数和模型。

#### 每次评估必须记录

- Git commit 和工作区是否干净；
- corpus hash、index version、chunk ID hash；
- chunk size / overlap；
- Embedding、Reranker、LLM 模型；
- BM25 k1 / b 和分词器版本；
- vector candidates / BM25 candidates / RRF k / fused candidates / final Top-K；
- Prompt 版本、temperature 和是否关闭 thinking；
- Python 与关键依赖版本；
- 运行时间、机器信息和是否预热；
- 每题原始结果、汇总指标和失败题。

#### 工具要求

新增只读校验命令：

```powershell
python -m scripts.verify_project_state
```

评估开始前必须检查：

```text
当前语料指纹
  = active manifest 语料指纹
向量 chunk ID 集合
  = BM25 chunk ID 集合
  = 当前切分结果 chunk ID 集合
```

任一不一致都应终止评估，而不是只打印警告继续运行。

#### 验收清单

- [ ] BM25 模式不再用向量条数代替 BM25 快照
- [ ] 每份结果都能定位到唯一代码和索引版本
- [ ] 参数变化能在两份结果的 metadata 中直接看出
- [ ] 同一 manifest 和参数可重新运行并得到指标级一致结果

### 阶段五：在最终语料上重做 chunk 实验

#### 学习目标

重新回答“为什么当前是 800/150”，避免继续引用旧的 10-chunk 语料实验作为最终依据。

#### 实验设计

第一轮只改变 `chunk_size`，固定 overlap：

```text
T2-1: 600 / 150
T2-2: 800 / 150（当前基线）
T2-3: 1000 / 150
```

选定 chunk size 后，第二轮只改变 overlap：

```text
T3-1: chosen_size / 80
T3-2: chosen_size / 150
T3-3: chosen_size / 220
```

每组必须在同一冻结语料、同一回归问题、同一模型和同一检索参数下重建两套索引并运行四模式评估。

#### 观察指标

- Recall@5 / Recall@10；
- MRR@10；
- 必要证据覆盖率；
- 同一来源相邻块重复率；
- Top-K 中不同来源数量；
- Prompt token 数；
- 索引 chunk 数与构建成本；
- 逐题改善与退化，而不只看平均分。

#### 决策规则

- 不预设 800/150 必须获胜；
- 如果新参数没有稳定改善，则保留当前值；
- 不能用保留测试集选择参数；
- 所有失败结果同样归档，不只保留获胜配置。

#### 验收清单

- [ ] 当前 111-chunk 语料完成至少三组 chunk size 对照
- [ ] 完成 overlap 单变量实验或记录不做的充分理由
- [ ] 最终参数有逐题证据，不再引用旧语料结论
- [ ] 参数变更后两套索引和 manifest 同步更新

### 阶段六：加固评估集与指标

#### 学习目标

理解开发集、回归集和保留测试集的区别；理解“命中任一相关块”和“回答所需证据完整”不是同一个指标。

#### 数据集设计

1. 当前 32 题改名为 regression set，可用于日常回归和错误分析；
2. 在生成端优化前新增至少 15 道 holdout 题并冻结；
3. holdout 至少包含：
   - 关键词型 2 题；
   - 语义改写型 3 题；
   - 相似章节干扰型 2 题；
   - 多证据型 4 题；
   - 拒答型 4 题；
4. 调优期间不根据 holdout 逐题结果修改系统；
5. 最终只在版本候选完成后运行一次 holdout 验收。

#### 多证据标注

对于一个事实可能出现在多个重复 chunk、而一个答案又需要多个不同事实的情况，新增 `evidence_groups`：

```json
{
  "id": "qxx",
  "question": "...",
  "relevant_chunk_ids": ["..."],
  "evidence_groups": [
    ["能支持事实 A 的 chunk-1", "同样支持事实 A 的 chunk-2"],
    ["能支持事实 B 的 chunk-3"]
  ]
}
```

同组内命中任一 chunk 即算该项证据命中；所有组都命中，才算必要证据完整。

#### 指标要求

- Any-hit Recall@5：至少一个相关证据进入 Top-5；
- Evidence-group Recall@5：必要证据组命中比例；
- Complete-evidence@5：是否命中所有必要证据组；
- MRR@10：第一个相关证据的排序；
- 严格引用准确率：每个被引用编号都直接支持结论；
- 引用块级精确率：支持引用数 / 全部引用数；
- 拒答准确率：区分“有拒答依据”和“知识库完全无相关内容”。

#### 验收清单

- [ ] regression 与 holdout 文件物理分离并各自冻结
- [ ] 多证据题不再只用 any-hit Recall 判定成功
- [ ] 报告不再笼统写“拒答题不计入”，而是说明具体排除口径
- [ ] 数据集校验脚本能检查 ID、来源、chunk 和 evidence group

### 阶段七：专项提升引用质量

#### 学习目标

在不改变检索器的前提下，定位 79.3% 引用准确率究竟来自 Prompt、上下文顺序、回答格式还是模型行为。

#### 实验顺序

每次只改变一个主要变量：

```text
C0：当前 Prompt，复现 79.3% 基线
C1：明确要求“只引用直接支持最终结论的最少资料，不要列出未使用资料”
C2：要求每个关键结论紧跟引用编号，禁止在文末批量罗列全部编号
C3：固定结构输出“答案正文 + 使用依据”，并校验引用编号范围
```

如果 C1 已经达到目标，不继续叠加 C2/C3。每轮必须保留原始答案并逐题比较新增错误与修复案例。

#### 质量门槛

| 指标 | regression 目标 | holdout 目标 |
|---|---:|---:|
| Recall@5 | 不低于 v2.0 | 不低于 85% |
| 答案正确率 | ≥ 90% | ≥ 85% |
| 严格引用准确率 | ≥ 90% | ≥ 90% |
| 引用块级精确率 | ≥ 90% | ≥ 90% |

## 7. 实验纪律

每次实验必须记录：

```text
实验编号：
问题与假设：
代码版本：
索引版本：
固定条件：
唯一主要变量：
regression 结果：
受影响题目：
成本与延迟：
结论：保留 / 回退 / 继续验证
```

必须遵守：

- 不修改知识库答案来修复评估失败；
- 不使用 holdout 结果选择参数或 Prompt；
- 改 chunk 参数必须发布一套新的双索引版本；
- 改问题标注必须记录理由并重新运行所有对照方案；
- 不只保留成功实验；
- 不用平均分掩盖某类问题退化；
- 不能通过降低指标或更换口径把未达标改写成达标；
- 外部 API 抖动要通过重复运行和指标级口径说明，不能直接归因于代码改善。

## 9. v2.5 结束后的决策方式

v2.5 完成后，不预先规定 v3.0 必须做什么，而是根据保留测试集的主要失败类型选择一条主线：

```text
陌生表达召回不足
  → Query Rewriting / Multi-Query

必要证据分散且无法完整召回
  → 父子块检索 / 上下文压缩

连续追问无法独立理解
  → 多轮对话与历史问题改写

引用仍不稳定但答案正确
  → 结构化生成 / 引用验证

链路已经复杂到难以维护
  → 再考虑用 LangChain 重构并做等价对照
```

在 v2.5 完成之前，不启动上述后续功能。
