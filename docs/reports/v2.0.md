# rag-one v2.0 版本报告

- 版本定位：召回、融合、排序与端到端评估
- 核心目标：在 v1.0 向量 RAG 上引入 BM25、RRF 和 Reranker，用固定数据集证明每一层的收益与成本
- 最终状态：**七个阶段完成；检索与答案指标通过，严格引用准确率未达到 90%**

> 本报告根据原始项目历史和 v2.0 人工评估记录重新拆分。文中的 `src/*.py`、`ingest.py`、`ingest_bm25.py` 是 v2.0 当时路径；v2.5 已完成包结构和索引发布重构。

## 1. 版本背景

v1.0 已经完成：

```text
文档加载 → 切分 → Embedding → 向量检索 → LLM回答 → 引用展示
```

但单一向量检索存在三个问题：

1. 编号、专有词和精确数字等关键词问题不一定稳定；
2. 向量召回只提供一条排名，没有第二种信号可以互补；
3. 召回模型擅长“快速找候选”，不擅长逐条精确判断问题与原文关系。

v2.0 将链路扩展为：

```text
问题 ─┬→ 向量召回 Top-20 ─┐
      └→ BM25召回 Top-20 ─┴→ RRF融合 → Reranker → Top-5 → LLM
```

四种可对照模式：

| 模式 | 链路 |
|---|---|
| vector | 纯向量检索 |
| bm25 | 纯关键词检索 |
| hybrid | 向量 + BM25 + RRF |
| hybrid_rerank | 混合检索 + Reranker |

## 2. 最终结论

| 层面 | 最终结果 |
|---|---|
| 冻结语料 | 10 个文件、15 条加载记录、111 个 chunk |
| 固定评估集 | 32 题，其中 31 题有相关 chunk 标注 |
| 向量基线 | Recall@5 96.8%，MRR@10 0.838 |
| BM25 | Recall@5 100%，MRR@10 0.888 |
| Hybrid | Recall@5 100%，MRR@10 0.925 |
| Hybrid + Rerank | Recall@5 100%，MRR@10 1.000 |
| E4答案正确率 | 32/32，100% |
| E4严格引用准确率 | 23/29，79.3%，未达到90% |
| E4拒答准确率 | 3/3，100% |
| 幻觉 | 0 |
| 自动化测试 | 65项通过，全部可离线运行 |

因此，v2.0 可以判定为“召回与排序链路完成，答案质量通过”，但不能写成“引用质量目标完成”。

## 3. 阶段一：冻结语料与评估标注

### 3.1 冻结语料

v2.0 将语料更新为 9 篇扩写版 Markdown 和 `10-faq.pdf`。PDF 共 6 页，因此加载后共有 15 条记录。

```text
10 个文件
15 条加载记录
111 个 chunk
平均 chunk 长度 717.7 字符
```

冻结脚本逐文件记录字节数和 SHA256 指纹，同时保存：

- chunk size / overlap；
- 文档与记录数量；
- 总 chunk 数和平均长度；
- 每个来源的 chunk 分布。

冻结期内所有检索模式共用同一份语料，不允许为某个实验单独修改文档。

### 3.2 扩充评估集

评估题从 25 道增加到 32 道，新增关键词、易混和语义问题。

| 题型 | 数量 |
|---|---:|
| direct | 9 |
| keyword | 5 |
| multi_source | 5 |
| confusable | 4 |
| unanswerable | 3 |
| reasoning | 2 |
| trap | 2 |
| table | 1 |
| semantic | 1 |

31 道题标注了 `relevant_chunk_ids`，共 103 个“题 × chunk”关系；q24为完全无依据的拒答题，没有相关 chunk。

标注只选择能够直接支持答案的规则句和数字，不把同主题的模板化扩写段算作相关证据。`expected_sources` 表示必须关注的来源，而 chunk 级标注允许 FAQ 等重复来源提供额外证据。

### 3.3 验收

独立脚本完成 384/384 断言：

- 文件指纹与冻结记录一致；
- 切分数量、平均长度和来源分布一致；
- Chroma 中 111 个 ID、原文、hash、metadata 和向量与当前切分一致；
- 32题ID连续唯一，来源和chunk标注合法；
- 9类问题各抽一题，相关证据均能进入Top-5。

## 4. 阶段二：建立向量检索基线

在加入BM25之前，先冻结纯向量结果作为共同基线。本阶段只测检索，不调用LLM，避免生成随机性掩盖检索问题。

### 4.1 统一指标

- Recall@5 / Recall@10：前K是否命中至少一个相关块；
- MRR@10：第一个相关块排得是否足够靠前；
- 相关块覆盖：Top-10命中了多少已标注相关块；
- 延迟：包含查询Embedding的单题端到端耗时；
- q24无相关标注，只记录返回内容，不进入Recall和MRR分母。

评估输出同时保存JSON和Markdown，并默认禁止覆盖已有基线。

### 4.2 基线结果

| 指标 | Vector基线 |
|---|---:|
| Recall@5 | 96.8%（30/31） |
| Recall@10 | 100% |
| MRR@10 | 0.838 |
| 相关块覆盖@10 | 84.8% |
| 延迟P50 / P95 | 198 / 574 ms |

唯一Recall@5失败题是q20：“外出拜访客户是否占用远程办公天数”。首个相关块排第7。

验收脚本独立重算375/375项断言；另一路径全量复跑的汇总指标一致。服务端Embedding在Top-8至Top-10近并列块之间存在小于0.001的顺序抖动，但Top-7和全部汇总指标稳定。因此项目把“可复现”定义为指标级一致，不要求弱相关末位逐项完全相同。

## 5. 阶段三：BM25关键词检索

### 5.1 实现

BM25由项目手写，而非引入`rank-bm25`：

- jieba精确分词；
- 去空白和纯标点，英文统一小写；
- 保存chunk、tokens、倒排表和平均文档长度；
- 查询词通过倒排表累积分数；
- 同分按chunk ID排序，确保确定性；
- 索引保存为可检查、可重建的JSON。

打分公式：

```text
score(q,d) = Σ IDF(t) × tf×(k1+1) / (tf + k1×(1-b+b×dl/avgdl))
IDF(t) = ln(1 + (N-df+0.5)/(df+0.5))

k1 = 1.5
b  = 0.75
```

使用Lucene式正值IDF，避免高频词产生负分。k1和b是查询打分参数，没有写死在索引内容中。

### 5.2 实验结果

| 指标 | BM25 | Vector | 变化 |
|---|---:|---:|---:|
| Recall@5 | 100% | 96.8% | +3.2pp |
| Recall@10 | 100% | 100% | 0 |
| MRR@10 | 0.888 | 0.838 | +0.050 |
| 相关块覆盖@10 | 93.3% | 84.8% | +8.5pp |
| 延迟P50 / P95 | 0 / 1 ms | 198 / 574 ms | BM25为本地内存检索 |

q20从第7升到第3，精确关键词和数字问题整体改善。BM25的弱点同样明显：

- q32语义题从第2退到第5；
- FAQ汇总块因为关键词密集容易排在前面；
- 多篇文档复用的模板段会一起进入Top-10。

两路形成互补：共同检出81个相关块，向量独有2个，BM25独有11个。

## 6. 阶段四：RRF混合检索

向量相似度与BM25分数的量纲和分布不同，直接相加会让某一路因为数值范围而不是质量主导结果。项目使用RRF，只根据名次融合：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
k = 60
```

每路默认取20个候选；同一chunk在两路出现时累加贡献，未出现在某一路时该路贡献为0。融合结果保留两路原始排名和分数，便于解释。

### 6.1 实验结果

| 指标 | Hybrid | BM25 | Vector |
|---|---:|---:|---:|
| Recall@5 | 100% | 100% | 96.8% |
| Recall@10 | 100% | 100% | 100% |
| MRR@10 | 0.925 | 0.888 | 0.838 |
| 相关块覆盖@10 | 91.7% | 93.3% | 84.8% |
| 延迟P50 / P95 | 195 / 458 ms | 0 / 1 ms | 198 / 574 ms |

相对向量路，Hybrid改善6题、零退化；q20从第7升到第3。相对BM25，改善4题，但q03从第1退到第2、q16从第2退到第3，仍在Top-3且Recall@5不受影响。

这两题展示了RRF的边界：RRF只能计算“多路名次共识”，无法阅读原文判断真假相关。特别是q16，几个候选的两路名次和相同，`1/(k+r)`的凸性会让名次更不均匀的组合略占优势。这不是实现错误，而是需要Reranker解决的粗排局限。

## 7. 阶段五：Reranker精排

### 7.1 设计

Reranker使用`BAAI/bge-reranker-v2-m3`。与可预计算文档向量的双塔Embedding不同，Reranker将“问题+候选文本”联合编码，能够逐词交互，排序更准但成本更高，因此只处理融合后的20个候选。

```text
向量Top-20 + BM25 Top-20
          ↓
       RRF Top-20
          ↓
       Reranker
          ↓
        Top-5
```

实现特征：

- 通过HTTP直接调用rerank端点，与OpenAI兼容的LLM端点分开；
- 请求返回全部候选分数，本地完成稳定排序和截断；
- 空候选不发请求；
- API错误抛出`RerankError`；
- 产品链路默认回退到Hybrid结果，严格实验可关闭回退；
- 保留`rrf_rank`与`rerank_score`，可以解释重排前后变化。

### 7.2 实验结果

| 指标 | Hybrid+Rerank | Hybrid | BM25 | Vector |
|---|---:|---:|---:|---:|
| Recall@5 | 100% | 100% | 100% | 96.8% |
| Recall@10 | 100% | 100% | 100% | 100% |
| MRR@10 | **1.000** | 0.925 | 0.888 | 0.838 |
| 相关块覆盖@10 | **94.8%** | 91.7% | 93.3% | 84.8% |
| 延迟P50 / P95 | 954 / 2057 ms | 195 / 458 ms | 0 / 1 ms | 198 / 574 ms |

31道计分题的首个相关块全部排第1。Hybrid遗留的q03、q16、q20、q32全部修复。

典型变化：

- q16相关块从RRF第4升到第1，重排分0.9687；
- q03差旅相关块从第4升到第1，无关费用块从第1降到第5；
- q20相关块从RRF第3升到第1，重排分0.9882；
- q32相关块从RRF第4升到第1。

成本是每题增加一次对约20个候选的调用：约8.1k输入Token，P50增加约760ms。收益为MRR提升0.075、覆盖提升3.1pp，并修复四个非满分排序案例。

## 8. 阶段六：端到端对照实验

检索实验完成后，v2.0选择E1纯向量和E4混合重排两条链路调用LLM，比较最终答案、引用、拒答、幻觉、Token和延迟。

### 8.1 预先约定的人工判定口径

- 答案正确：核心结论与期望一致；错误拒答判错；
- 严格引用正确：答案中的每个引用都必须包含直接支持结论的依据；
- 主题相关但不直接支持的块算错误引用；
- 三道拒答题不进入引用准确率分母，单独统计拒答准确率；
- 答案中没有证据支持的新事实计为幻觉。

### 8.2 质量结果

| 答案正确率 | 93.8%（30/32） | 100%（32/32） | ≥80% | 均通过 |
| 严格引用准确率 | 62.1%（18/29） | 79.3%（23/29） | ≥90% | 均未通过 |

E4每题比E1多付约0.95秒，换来答案正确率提升6.2个百分点、严格引用提升17.2个百分点、Top-5相关块覆盖提升20.7个百分点。

### 8.4 失败案例

**q20：检索缺陷向生成传导。** E1的正确证据没有进入Top-5，模型错误拒答并引用不支持的块；E4通过BM25、RRF和重排把正确证据提升到首位，最终回答正确。

**q12：生成端退化。** E1的Top-5已经包含“不能跨周累计”的直接原文，但模型仍回答无法确定。这个案例证明检索正确不等于生成正确。

**引用多标。** 两条链路的主要引用错误不是越界编号，而是模型把Top-5中主题相关但不支持结论的模板块一起列为引用。Reranker改善了上下文质量，但没有从根本上解决生成端乱引问题。

### 9.1 四链路追踪

### 9.2 索引重建安全

v2.0向量索引采用：

```text
先完成Embedding
→ 写入staging集合
→ 校验条数与可读性
→ 删除旧集合
→ staging改名接管
```

Embedding、staging写入或校验失败时，旧索引保持不变；BM25使用临时文件加`os.replace()`原子替换，并在重建后清除进程内缓存。

这里仍有一个后来在v2.5修复的边界：v2.0的向量切换包含“删除旧集合→重命名staging”的窗口，并不是真正的双索引原子发布；向量和BM25也仍可被分别更新。v2.5因此改为不可变双索引版本和单一active pointer。

## 11. 重要决策与踩坑

1. **BM25手写实现。** 公式、分词、倒排表和并列规则可解释，便于学习和独立复算。
2. **RRF只使用名次。** 避免余弦相似度和BM25分数的量纲问题。
3. **Reranker只处理窄候选池。** 精排准确但成本高，不能替代宽召回。
4. **失败可回退。** Rerank API失败时产品链路退回Hybrid，严格实验则抛错。
5. **语料冻结必须字节级。** 一次分隔线改动曾造成当前语料、Chroma和BM25不一致，证明实验前必须核对语料指纹、切分和索引三方状态。
6. **服务端向量存在微小抖动。** 跨时段比较应以相关块位置和汇总指标为主，不要求弱相关末位完全相同。
7. **显示分数不能用于重算排序。** RRF产物展示时四舍五入，复现必须使用完整精度重新计算。
8. **模板扩写段是hard negative。** 它们用于检验混合检索和引用是否能排除“主题相似但不支持答案”的文本。
9. **严格引用与答案正确是不同指标。** 答案事实正确，不代表每个引用都直接支持结论。
10. **低Rerank分可以观察，但尚未形成拒答阈值。** q24首位仅0.0151，计分题最低首位约0.1349，但v2.0没有据此直接加入阈值逻辑。

## 12. 完成情况与遗留问题

v2.0七个实施阶段全部完成：语料冻结、向量基线、BM25、RRF、Reranker、端到端对照、工程化与界面升级均有实现、测试和实验结果。

明确未完成的质量目标：

- E1严格引用准确率62.1%；
- E4严格引用准确率79.3%；
- 两条链路均未达到90%；
- 主要原因是生成端“多标编号”，不是引用编号越界；
- v2.0索引切换仍不是向量与BM25的统一原子发布；
- regression与最终holdout尚未严格分离；
- 多证据问题仍主要依赖any-hit判断。

这些问题成为v2.5的直接输入：统一版本状态、重构项目目录、实现不可变双索引发布、补齐复现metadata、建立regression/holdout纪律、增加evidence groups，并专项处理引用质量。
