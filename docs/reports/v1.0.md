# rag-one v1.0 版本报告

- 版本定位：RAG 最小可行产品（MVP）
- 核心目标：不依赖 LangChain/LangGraph，手写一条透明、可验证的中文 RAG 链路
- 最终状态：**七个阶段全部完成，MVP 完成定义 10/10 达成**

> 本报告根据项目最初的开发历史拆分整理。文中的 `src/*.py`、`ingest.py` 等路径是 v1.0 当时的目录；v2.5 已将运行代码迁移到 `src/rag_one/`，请勿把历史路径当作当前运行说明。

## 1. 版本目标与学习原则

v1.0 要完成一个“个人文档问答助手”：导入本地 Markdown、TXT、PDF，用户提问后先检索相关内容，再让大模型依据检索结果作答，并展示引用来源。

完整链路：

```text
文档加载
  ↓
文本清洗与切分
  ↓
Embedding 向量化
  ↓
写入 Chroma 向量数据库
  ↓
用户问题向量化
  ↓
相似度检索 Top-K
  ↓
组装上下文和 Prompt
  ↓
LLM 生成带引用的回答
```

本版本遵循三条原则：

1. 先验证检索，再接入生成；
2. 先让数据结构、分数和引用透明，再考虑框架封装；
3. 所有核心模块手写，避免在尚未理解链路时引入大型 RAG 框架。

## 3. 阶段一：知识库与评估集

### 3.1 知识库

v1.0 使用虚构的“星云科技公司制度手册”，共 10 篇 Markdown：

```text
01-company-overview.md
02-onboarding.md
03-attendance.md
04-leave-policy.md
05-expense-policy.md
06-travel-policy.md
07-remote-work.md
08-information-security.md
09-it-support.md
10-faq.md
```

语料刻意包含容易混淆的规定，用于观察检索与生成是否真正找对依据：

- 普通报销期限为 30 个自然日，差旅报销为返程后 15 个自然日；
- 住宿标准随城市类别和职级变化；
- 正式员工与试用期员工的远程办公规则不同；
- 病假、事假、年假的申请时限和证明材料不同；
- IT 服务请求与信息安全事件使用不同报告渠道。

### 3.2 评估集

## 4. 阶段二：文档加载

### 4.1 设计

`load_file()` 根据扩展名分发到 TXT、Markdown 和 PDF 加载器，并统一输出：

```python
{
    "text": "文档内容",
    "metadata": {
        "source": "01-company-overview.md",
        "page": 12  # 仅 PDF 存在
    }
}
```

关键设计：

- 路径锚定项目根，不依赖启动命令的当前目录；
- PDF 使用 PyMuPDF 逐页提取，页码从 1 开始，空页跳过；
- 单个文件读取失败、空文件或损坏 PDF 返回空列表，不中断整个目录；
- 目录加载按文件名排序，保证后续 chunk ID 和实验顺序稳定。

### 4.2 实测与验收

```text
文档数：10
记录数：10
总字符数：7220
```

17/17 边界断言通过，覆盖正常 TXT、空文件、纯空白、GBK 文件、损坏 PDF、多页 PDF、PDF 空页、未知扩展名和目录批量加载。

## 5. 阶段三：文本切分

### 5.1 参数与算法

```text
CHUNK_SIZE = 800
CHUNK_OVERLAP = 150
```

切分采用滑动窗口。窗口右端优先选择 `\n\n`、`\n`、`。`，且断点必须位于窗口后半段，避免产生过短碎块。完成一块后回退 150 个字符形成重叠，并使用 `max(end-overlap, start+1)` 防止死循环。

ID 规则：

```text
Markdown/TXT：06-travel-policy.md:chunk-2
PDF：guide.pdf:page-12:chunk-2
```

每个 chunk 保留 `source`、`chunk_index` 和可选 `page`。

### 5.2 实测与验收

v1.0 的 10 篇短文均小于 800 字符，因此得到 10 个 chunk，平均长度约 721 字符。

34/34 断言通过，覆盖：

- ID 全局唯一、格式稳定、metadata 完整；
- PDF 页码正确传递；
- 两次独立切分结果完全一致；
- 硬切文本精确重叠 150 字符；
- 段落文本优先按自然边界切分；
- 空文本、纯空白、短文本和空列表汇总均不报错。

## 6. 阶段四：向量索引

### 6.1 处理流程

```text
加载 → 切分 → 批量 Embedding → 写入 Chroma → 持久化
```

主要模块职责：

- `config.py`：读取 `.env`、模型和路径配置；
- `embeddings.py`：调用 `BAAI/bge-m3`，自动分批并按返回 index 恢复顺序；
- `vector_store.py`：封装 Chroma PersistentClient、集合和 upsert；
- `indexer.py`：串联全流程，并给 metadata 增加内容 MD5；
- `ingest.py`：全量构建命令入口。

关键配置：

| 参数 | 值 |
|---|---|
| Embedding 模型 | `BAAI/bge-m3` |
| 向量维度 | 1024 |
| Chroma 集合 | `rag_mvp_docs` |
| 距离 | cosine |
| Embedding batch | 32 |

Chroma 返回余弦距离，展示相似度时使用 `score = 1 - distance`。

### 6.2 实测与验收

全量构建结果：10 篇文档、10 个 chunk、10 条向量；连续运行两次没有重复数据。

23/23 断言通过，覆盖：

- 新进程可读取持久化集合；
- 索引 ID、原文、source、chunk index 和 MD5 与切分结果一致；
- 全部向量为 1024 维；
- 使用自身向量查询时 Top-1 为自身且距离接近 0；
- 强制小 batch 后顺序仍正确；
- reset 后可以完整重建。

语义冒烟问题“普通员工去上海出差，酒店住宿每晚最高报销多少”首位命中《差旅制度》。

## 7. 阶段五：Top-K 检索

检索流程：

```text
问题 → embed_query → Chroma Top-K → 解包平行列表 → 结构化命中
```

输出字段包括 `rank / id / score / distance / source / page / text`。默认 `top_k=5`，可传参覆盖。

关键实现点：

- Chroma 查询返回“查询数 × K”的嵌套列表，单问题统一取第一层；
- 使用 `zip` 对齐 IDs、documents、metadatas 和 distances；
- rank 连续，距离升序，score 与 distance 严格满足 `score=1-distance`；
- `format_hits()` 是纯展示函数，不访问数据库。

验收结果：20/20 结构与边界断言通过。25 题检索评估中，可计分来源共 31 个，来源级 Recall@5 为 **31/31，即 100%**。

### 7.1 T1 分块实验：800/150 与 400/150

| 配置 | Chunk 数 | 来源级 Recall@5 | q01 首位来源 |
|---|---:|---:|---|
| 800/150 | 10 | 100% | 差旅制度 |
| 400/150 | 32 | 93.5% | FAQ |

更细的块没有提升检索：短文原本就是完整语义单元，切成 400 字符后语义被打断，同篇相邻块还会挤占 Top-5。结论是恢复并保留 800/150。

另一个重要发现是：库外问题仍会返回五个“相对最相似”的结果。检索器本身不会判断资料是否足以回答，拒答必须由后续生成逻辑处理。

## 8. 阶段六：答案生成

完整问答流程：

```text
问题 → retrieve → 将 Top-K 编号为 [1]...[K] → 组装 Prompt → LLM → 带编号答案
```

`ask()` 返回问题、命中列表、答案和 Token 用量，保证回答中的 `[N]` 可以映射到 `hits[N-1]`。

生成参数：

| 参数 | 值 | 原因 |
|---|---|---|
| LLM | `Qwen/Qwen3-8B` | 中文制度问答 |
| temperature | 0.2 | 降低随机性，便于复现 |
| thinking | 关闭 | 避免约 400 个无必要思考 Token 和约 15 秒延迟 |
| 上下文 | Top-5 chunk | 在依据覆盖和成本之间取初始平衡 |

18/18 断言通过。三类端到端样例验证：

- q01：正确回答 700 元，并引用《差旅制度》；
- q11：正确回答远程办公限制，引用可追溯；
- q24：知识库无依据时回答“根据现有资料无法确定”。

当时已观察到拒答答案仍可能附带资料编号，v1.0 接受该限制，留给后续版本改善。

## 9. 阶段七：Streamlit 界面

页面只调用已有 `build_index()` 和 `ask()`，不复制核心检索或生成逻辑。

主要功能：

- 上传 Markdown、TXT、PDF 并保存到知识库；
- 一键重建向量索引；
- 输入问题并展示答案、Token、Top-K 来源与原文；
- 使用 `session_state` 保留结果，避免 Streamlit 重跑导致答案消失；
- 对问答和重建异常显示错误，不让页面崩溃。

使用 Streamlit AppTest 完成 24/24 断言，并补验真实上传路径。覆盖首屏、空输入、q01问答、五个检索折叠区、Token展示、重建、问答失败、重建失败以及上传保存。

## 11. v1.0 关键经验

1. Windows 中文环境统一使用 `-X utf8`，避免 GBK 输出问题；
2. 项目统一使用独立 Conda 环境，避免系统 Python 与项目依赖混用；
3. Chroma 集合必须显式关闭内置 embedding function，向量全部由项目传入；
4. 集合距离等建表参数只在新建时生效，修改后必须重建；
5. 切分不是越细越好，应根据语料结构用固定问题集验证；
6. Top-K 检索永远会返回相对结果，不能仅凭“有结果”判断可回答；
7. Prompt Token 通常远多于 Completion Token，成本优化应优先关注 chunk 和 Top-K；
8. Qwen3 的思考模式对简单文档问答成本高，应显式关闭。

## 12. 已知局限与下一版本入口

- 只有向量检索，对编号、专有名词和精确数字不够稳定；
- 没有 BM25、融合和重排；
- 索引重建采用覆盖式流程，失败恢复和版本一致性不足；
- 评估主要关注来源级 Recall，尚未系统衡量 chunk 排名、答案和引用质量；
- 引用依赖模型输出，缺少严格人工判定；
- PDF 仅支持文本提取，不支持 OCR、图片和表格专项解析。

这些问题成为 v2.0 的输入：冻结语料，建立可重复基线，引入 BM25、RRF 与 Reranker，并进行四模式和端到端对照实验。
